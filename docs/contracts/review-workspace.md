# Bounded join and meeting publication helpers

`inspectJoin` is a pure calculation over two explicitly supplied relations, read from a join request (`joinInspectionSchema`, `src/intelligence/joinInspection.ts`; strict, unknown fields refused). Both aliases differ, rows and columns have stable unique IDs (lowercase, at most 80 characters), and types (string, number, boolean) and nullability are explicit. Limits: 200 rows per relation, eight columns, one to four key pairs, 12 source IDs, text of at most 160 characters, cell strings of at most 500, finite numbers within 1e12, preview 1-100 rows (default 40). Supported joins: inner and left equijoin with exact typed equality. NULL never matches NULL; implicit casts, collation, temporal predicates and SQL execution are not implemented. A `source-derived` request needs cited source IDs; a `synthetic` one stays labelled synthetic in every block it produces.

The public synthetic fixture `examples/review-workspace/join.request.json` is the request of the worked example: four invented order lines summing to 42 illustrative EUR, three customer versions, an inner join on `customer` expecting one match. It gives four output rows summing to 70, with `line.c` and `line.d` unmatched. `tests/review-workspace.test.ts` checks that the committed file equals the builder output (`joinRequestJson()` in `examples/review-workspace/build.ts`) byte for byte; `.gitattributes` keeps its LF bytes on every checkout.

Output reports both unmatched rows and fanout, exact output count within the supplied cohort, a bounded preview, and row correspondence. An optional additive left numeric measure is shown before and after alongside missing inputs. No population-wide correctness is inferred from samples or a `declared-complete` label. JavaScript numbers are not a decimal accounting engine. The helper does not infer that every fanout is wrong: multiplicity must be declared.

`joinInspectionBlocks` returns six ordinary transformation blocks (two inputs, logic, output, mapping, rules). All default PRIVATE, including synthetic requests. An explicitly authored public synthetic fixture may publish its own blocks. Source IDs must resolve in the owning Project; `validateDocument` remains required. No observations/review/authority is created.

`meetingSummaryHtml(Project, PublicationBrief, {now?})` uses the existing publication-brief contract, native overview projection and SVG renderer; `meetingSummaryFile(Project, PublicationBrief, now?)` returns `{fileName, html}` with the file name `<project id>.meeting-summary.html`. Both apply the public projection themselves, so passing the author project is safe. Limits (`MEETING_SUMMARY_LIMITS`): title and audience at most 160 characters, one to six selected public views. Supported profiles: design and business. A4/letter print CSS, or A4 print fallback for screen-oriented input. Refusals are explicit and change nothing: more than six views, another profile, a duplicate selection, a story stop outside the selected views, and a private or unknown view ID, which get the same reason ("Publication references an unavailable public view") so a refusal never reveals that a private view exists. `meetingBriefChoices(Project)` lists what a brief may select: public views reachable from the public root by childViewId drilldown (through `publicDocument`), the public story length and the two profiles. Overview intentionally omits evidence bodies; standard/full include selected public blocks, so a selected join's rules block shows "Measure before 42" and "Measure after 70" for the worked example. Synthetic blocks carry the visible label "Synthetic example data, not a measured result." The output is offline: Content-Security-Policy `default-src 'none'`, no script, no external stylesheet, font or image, and glossary links move keyboard focus to their section.

The App entry point is **Export & share > Meeting summary**: `src/ui/MeetingSummaryDialog.tsx` (`MeetingSummaryDialogProps={project, activeViewId, onDone, onCancel}`) offers labelled fields for title, audience, views (the current view preselected when it is a public reachable view), detail, paper, profile and optional story stops, validates through `validatePublicationBrief` and downloads the file. It states the fidelity note: browser print gives the PDF, the PDF is a snapshot, not a backup, and no PPTX is produced here. Mounting it in the export menu is the integrator's change to `src/App.tsx`. Dense diagrams use an explicit fallback and complete component list, not unreadable microtype. It is a static, self-contained public HTML publication, not a full source backup or a private hosting system. Source-derived public captions backed by private sources are suppressed with existing overview rules.

The existing linked HTML reader also supports moving ONE detail dock below both views or below the companion. Closing the companion temporarily returns the same dock to the bottom; reopening restores its selected placement. This is a bounded exported-reader composition, not a new arbitrary docking engine or proof of integrated App state. It preserves exact/mapped selection, independent cameras and the business anchor from F/G.

Prepare the original synthetic example explicitly in a fresh output directory:

```sh
./node_modules/.bin/tsx scripts/prepare-review-workspace.ts --example NEW_DIRECTORY
```

The command generates ordinary Project/reading/publication JSON, a join request/result, interactive reading HTML and a static meeting summary. It never executes SQL, connects to a provider or overwrites an existing directory. The App can consume ordinary Project JSON through its normal validation route; new helpers are not extra automatically accepted top-level JSON formats.

The command writes `review.project.json`, `review.reading.json`, `review.publication.json`, `join.request.json` (identical to the committed fixture), `join.result.json`, `join-review.html` and `meeting-summary.html` into the new directory only (`EEXIST` otherwise).

Native source checks: `tests/join-inspection.test.ts`, `tests/meeting-summary.test.ts`, `tests/review-workspace.test.ts`, and the offline browser checks `tests/e2e/meeting-summary.spec.ts` (summary file at 1440 and 390, print media, form markup at 390) and `tests/e2e/review-workspace.spec.ts`. Integrated browser testing, publication byte/fidelity inspection, actual client storage and full required gates remain the native lead's responsibility.
