# Authored question answers and recorded review

`diagramcloud.question-answer/1` is a bounded convention in ordinary private JSON code evidence, not a Project schema, observation, execution or approval format. Existing explanation-details/1 reading is unchanged. Companion → Questions reads answers in private Explore and permits proposals only when its host supplies Edit mode and `onPropose(patch: Patch)`. The host owns normal patch review, Apply, revision, Undo and save. No mutation occurs on typing or proposal creation. No network, provider, autonomous answer generation or automatic review occurs.

Each record names the subject node and exact explanation-details block ID; the full source basis fingerprint; question kind, index and exact text; answer text (1–1600 characters), named author (1–160), up to eight distinct existing citation IDs and their content fingerprint. The source basis includes non-answer node semantics, all attached non-answer evidence, their source records and image assets. Answer memberships/content are excluded, so editing/reviewing one answer does not invalidate siblings. The existing canonical/FNV64 content fingerprint authority is used for drift detection, not a cryptographic signature or authorization proof.

Index or text alone is never identity. Any source-block content change, source/citation drift, changed node semantics, question reordering or missing question makes the old binding stale. Duplicate question text (including focus versus follow-up) is conservatively unavailable. Multiple answers claiming the same full binding are ambiguous; unsupported/malformed attached answer records prevent new proposals rather than being merged or overwritten. Old/stale records remain in ordinary evidence and full authoring backups; Questions exposes their original JSON in a read-only copyable field. New answers may be proposed against a new unambiguous source cut, while old records remain visibly stale. There is no automatic rebase, merge or delete.

Review is an explicitly proposed named attribution with UTC timestamp and fingerprint of the answer, its binding and cited records. It means “this review was recorded under this name”, not authenticated identity, observed truth, correctness or release approval. The UI asks the operator to record only a review actually performed by the named person. Any answer edit removes prior review; changing source/citation content makes the old review stale. Importing a record cannot establish that a real person performed its claimed review.

Proposals retain the source Project revision and full JSON Patch tests of nodes, blocks, sources and assets. Apply refuses a changed revision or same-revision source/answer drift atomically through the existing patch authority. These broad tests intentionally reject unrelated concurrent changes too; reopening is safer than rebinding silently. The component retains pending text and its original binding read-only when Project/revision/source/answer scope changes. An explicit Start from current question action discards that pending form and loads the current saved answer. This is also required after Apply; no form silently rebinds. Closing Questions or changing component/public mode unmounts unsaved forms; pending text is not an autosaved draft. Only applied answer records enter Project backups. Existing explanation-request draft recovery is a separate capability.

Public mode does not mount this answer UI, and generated answer blocks are always private. Existing publicDocument remains the export authority. No changes were made to the explanation compiler, observation authority or Project schema. Missing or unsupported question records leave retained answers readable without exposing edit/review controls.

Focused qualification: question-answers.test.ts checks binding, drift, duplicate/unsupported refusal, exact patch guards, reload/history and public projection. question-answers.browser.mjs exercises the real Companion with a host harness at1440/390, including explicit proposal/Apply, review/edit, Undo/reload, source conflict and public unmount. This component harness is not an actual App integration receipt; the integrating host must qualify stagePatch wiring and modal focus return in the full workspace.
