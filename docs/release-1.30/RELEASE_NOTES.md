# DiagramCloud 1.30.0: V3 workspace

A minor release on top of [1.29.1](../release-1.29/RELEASE_NOTES-1.29.1.md). Document schema stays 1; the model gains one optional field (`tourStop.referencedFingerprint`). V3 is integrated, not complete: the acceptance rows UX26-UX34 in [V3_WORKSPACE](../product/V3_WORKSPACE.md) say which are implemented, with the test that proves each one, and which stay partial.

## What changed

- **Foundation and PM task import** ([#102](https://github.com/julian-passebecq/diagramcloud/pull/102), UX28). Four handoff patches are adopted: parent-preserving view routes and workbench layout presets, reading perspectives and a history lane over supplied records, capability briefs and usage arithmetic, and a reader of PM's `datapass.owner-tasks/1`. An existing PM task file enters through the ordinary import dialog as a private, read-only projection with state, dependency and detail views. It is bounded (60 tasks, 1000 dependency links, 256 KiB) and refused whole, without mutation, when invalid, cyclic or larger. A task's DONE or APPROVED is a source-declared state, never a DiagramCloud review or an observation. Nothing is written back to PM and no session is launched.
- **V3 workspace** ([#106](https://github.com/julian-passebecq/diagramcloud/pull/106)). The **V3 workspace** header button (or `?workspace=v3`) shows the same project in an explorer, view, companion and dock frame built from the existing components. Every view jump keeps the reader's chosen parent, asks when several parents exist and refuses a revoked path generically. Each move is one browser history entry and a deep link. An unapplied form edit holds every route change behind Keep editing / Discard. Every pane, hidden or visible, reads the permitted projection, and a pin never crosses into the public copy. At 390x844 one pane shows at a time.
- **Capability examples** ([#103](https://github.com/julian-passebecq/diagramcloud/pull/103)). Two capability guides compile into ordinary projects: DiagramCloud describing itself, every statement citing a file and line at source cut `ecf4af6`, and a synthetic document question-answering service labelled synthetic throughout. **Load capability brief** in the workspace explorer opens a brief in the import review; nothing is applied, executed or reviewed for the author.
- **Linked comparison** ([#107](https://github.com/julian-passebecq/diagramcloud/pull/107)). The workspace's Compare task opens a variant, two revisions of the session or two declared environments side by side. Objects pair by exact stable ID (across projects only by a recorded correspondence); an absent counterpart is shown as absent; selecting never applies anything. A source change marks the comparison stale and never re-pairs. Return restores the reader's view and selection.
- **Interruptible presentation** ([#108](https://github.com/julian-passebecq/diagramcloud/pull/108)). A playing tour can be paused for a question. The presenter can inspect, zoom out or drill, then Return and resume at the same stop, found by its identity. A source change or an audience change during the pause is reported and offered as a choice, never followed silently. Permissions are checked again for the audience on return.
- **Expressiveness complement** ([#104](https://github.com/julian-passebecq/diagramcloud/pull/104), [#105](https://github.com/julian-passebecq/diagramcloud/pull/105), [#109](https://github.com/julian-passebecq/diagramcloud/pull/109), UX31-UX34). Explanation walkthroughs (`npm run explain`), whose patch enters the App through the ordinary JSON review. A companion pane in the workspace shows explanation, code/state, related context (drawn with the export scene, with a keyboard list alternative and bounded filters) and evidence, and opening a related item is a detour with an explicit return. "Focused explanation HTML" is its own export option, and there are six synthetic teaching examples. A tour stop now also fingerprints the content its subjects reference, so a changed reference makes it stale.
- **Integration.** Version 1.30.0. One release journey (`tests/e2e/v3-release.spec.ts`) runs through the real App with every non-loopback request aborted: workspace, PM import, Follow/Pin, capability example, comparison, presentation with a detour and resume, and an offline HTML export. It found that recording a tour left the workspace's unsaved-edit guard armed, so the next mode change asked about an edit that had already been used. The tour record buttons now submit their form, which clears the guard.

## Limits

- PM import is read-only, private and bounded: no write-back, no launch, no session, no observation. Its public projection is a neutral empty shell.
- Estimates in the handoff (effort, dependency bounds, tokens) are uncalibrated planning allowances, not measurements, bills or approvals. `usageEconomics` does arithmetic over supplied records only and is not shown in the App.
- Preparation is never execution: a prepared plan, prompt or brief is not a run, a review or a release.
- UX26 (handoff identities) and UX27 (ownership and fileset conflicts) are recorded in documentation only; the App has no view for them. UX30 (plan to release chain) is partial: the PM task views and the history lane over atlas snapshots exist, prompt, native result, qualification and release links do not.
- The workspace has no free drag docking, no saved layouts, no builder identities and no Git, work, question or decision dock panels. Walkthrough requests are still written as JSON and compiled by the CLI (no in-App request editor), and the printed form of the focused HTML export is not inspected (UX33 partial).
- The VS Code and Cursor host tests still run on a local desktop only; extension update, signing and Marketplace are not proven. Only Chromium is qualified.
