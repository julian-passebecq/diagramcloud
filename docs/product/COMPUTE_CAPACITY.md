# Compute capacity scenarios

In the author workspace, open the bottom **Workflow** tab and expand **Compute capacity scenario**. The form performs CU arithmetic over explicitly supplied assumptions. It does not model staff or agent availability, schedule work, predict a finish date, query a provider or dispatch anything.

Choose **Supplied usage share** to enter a basis, capacity in CU, usage in CU-seconds and reporting duration in seconds. **Calculate compute scenario** calls the existing `capacityShare` function. The result shows the supplied basis and numerator, the capacity-window denominator and the percentage. Changing the reporting window changes that percentage; a total does not establish concurrent peaks or service behavior.

Choose **Activity and floor scenario** for explicit resource IDs, start/end offsets, a reporting interval, idle tail and per-resource floor. The existing `onlineIntervals` and `floorScenario` functions merge overlapping activity/tails only for the same exact resource ID and clip them to the reporting interval. The result shows the merged intervals, online resource-seconds, floor CU-seconds, percentage and the engine's exclusions. Resources with similar names are not matched. Times share one numeric origin and are not calendar dates. The UI accepts at most 100 activity rows; the engine retains its separate existing bound.

Inputs start blank. Blank is unknown; a supplied `0` is zero where permitted. Capacity and reporting duration must be positive. With no supplied activity rows, calculation is refused unless the author explicitly assumes no contributing activity **or idle tails** for the interval. This distinction matters because earlier activity can leave a tail in the reporting interval. No example inputs are loaded automatically. Basis text is the author's declaration, not reviewed evidence or an observed claim.

Inputs are checked for finite values, invalid duration, bounds and numerical overflow/underflow. Positive usage or floor that would round to a zero result is refused; an idle tail that disappears at extreme numeric offsets is refused. Ordinary floating-point arithmetic remains the existing engine's authority, not a provider's accounting precision or calibration. Values above 100% are displayed without implying simulated throttling or billing.

Every form edit clears the previous result and errors; recalculation is explicit. The draft remains only in component memory. Closing the disclosure keeps its draft within that session but removes its form controls from the DOM, so hidden controls cannot trap keyboard focus. Clear removes the draft. A project/revision change or entering public mode unmounts it; returning to author mode starts blank. No Project mutation, Undo entry, storage record, observation or export is created. The current implementation offers no result persistence or publication action.

Source: `src/ui/CapacityScenarioPanel.tsx`, `src/ui/capacityScenarioDraft.ts`, and a small author-only mount in `ProjectDock.tsx`. The parser only decodes form input and refuses unrepresentable results; all capacity arithmetic remains in `src/intelligence/capacityScenario.ts`.

Validation: the existing capacity engine suite plus `tests/capacity-scenario-draft.test.ts` cover explicit denominators, zero/unknown, same/different resource identities, clipping, invalid inputs and numeric bounds. `tests/e2e/capacity-scenario.spec.ts` exercises the real App at 1440×1100 and 390×844, including keyboard disclosure/calculation, stale-result clearing, private audience/project/revision resets, unchanged canonical Project/Undo, and keyboard focus after removing an activity at the 100-row limit. Qualification results belong to the selected source receipt, not this feature description.
