# DiagramCloud for AI agents

This page is for an AI agent (Claude Code, Codex, any LLM with a shell) that has to graph a repository or a set of projects with DiagramCloud, edit a DiagramCloud document safely, or draw publication figures. Read it once, then work from the command table. The JSON examples on this page are checked by `tests/ai-guide.test.ts` against the real validators, so they are valid as written.

## 1. What DiagramCloud is

- **A document model, not a drawing.** A project is one JSON document (`diagramcloud.json`, schema version 1). It has components (`nodes`), connections (`edges`), views that each show a subset with positions, evidence blocks, sources, a guided story and optional observations. `src/core/model.ts` is the contract and `validateDocument` is the gate: JSON Schema alone (`public/diagramcloud.schema.json`, written by `npm run generate`) is not enough.
- **Facts come from repositories, not from memory.** A deterministic scanner reads a folder (no code run, no network, no secret files) and produces components and links, each with file:line evidence and a confidence. An atlas joins several repositories, each at **its own Git revision**: there is never one project revision.
- **Drawing is a separate layer.** Diagram Design mode renders any public view as one of 23 figure types. You choose the figure through a *design brief*; you never change facts to make a picture look better.
- **Public vs private is enforced.** Public exports go through `publicDocument`, which drops private components, connections, evidence and repositories. Authoring JSON is the explicit full private backup. Mark something `"visibility": "private"` instead of leaving it out.

## 2. Three meanings you must keep apart

| Meaning | Where it lives | Who sets it |
|---|---|---|
| **Planned / designed** | a component's `status` (`idle`, `running`, `complete`, `warning`, `failed`) and `basis: "planned"` | the author or the manifest |
| **Read from source** | `basis: "static-source"`, scanner evidence with file:line | the scanner |
| **Observed / verified** | `observations` (dated external claims) | a human, through a reviewed patch only |

A scan is never "observed". A status board shows designed status, not reality. Synthetic or illustrative numbers stay labelled `"provenance": "synthetic"` everywhere and are never results.

An external observation can optionally carry `stateFacet: {facet, value, scope}`. The six independent axes are `lifecycle`, `selection`, `implementation`, `verification`, `distribution` and `runtime`. `value` and `scope` are explicit nonblank source text (at most 160 characters each), preserved in the producer's vocabulary; scope is an inert label, never a membership or access grant. For example, a source may report lifecycle `FROZEN` and distribution `DEPLOYED` for the same component. `CANCELLED` never removes code or implies a runtime state. Owner, source, date and revision come from the enclosing observation. Use the existing revision-guarded observation patch and human review; never infer a facet from a summary, missing commits, folder digest or design status. Missing axes stay unknown. Dated claims, histories and disagreements remain separate; there is no current-state verdict. Typed facets do not create a general Verified component badge. Public export retains only reviewed public observations. Other view adapters may omit scoped states; use the observation history or full public JSON to retain them.

## 3. Commands

All commands run from the repository root after `npm ci`. They read files and write files; none of them changes the input document.

| Goal | Command | Output |
|---|---|---|
| Graph one repository | `npm run scan -- <folder> --out repo.json [--name "Title"]` | a validated document: system → containers → components → files, data lineage, infrastructure |
| Graph several repositories | write a project manifest (section 4), then `npm run atlas -- project.manifest.json --out atlas.json` | one atlas document, each repository at its own revision |
| Keep private provenance for a new Galaxy import | `npm run atlas -- galaxy.json --capture-galaxy-provenance --out .local/atlas.private.json` | full authoring JSON with an optional private import receipt; no namespace binding or ID reuse |
| See what moved since last time | `npm run atlas -- project.manifest.json --previous atlas.json --out atlas2.json` | a new snapshot; the report lists changed / unchanged / unknown revisions |
| Draw every public view | `npm run design -- doc.json --out figures/` | one SVG per view, `index.html`, `book.html` (figure book) and `suggestions.json` |
| …with your figure choices | add `--brief brief.json` | the brief is applied in memory and its review printed |
| …as PDF | add `--pdf` | `book.pdf` and one PDF per view (offline Chromium; `npx playwright install chromium` once) |
| …one figure type for all | add `--type <type>` and/or `--theme light\|dark\|editorial` | |
| Before / after a rescan | `npm run design -- new.json --delta old.json --out figures/` | Before · Changes · After per view, compared by stable ID |
| Prepare a Mosaic concept preview | `npm run concept:preview -- doc.json --view root --audience public --out new-preview/` | concept JSON, typed source mapping, host sidecar and a local receipt; output must be a new directory under an existing parent |
| Open a selected local owner viewer | `npm run concept:host -- doc.json --view root --audience public --viewer concept-viewer.html --viewer-sha256 <sha256>` | isolated loopback host; no renderer download, source collection or publication; optional matching `--packet` and explicit `--diagramcloud-origin` enable bounded mapping return |
| Check your edits | `npx tsc --noEmit`, `npm test`, `npm run build`, `npx playwright test` | the qualification a change needs before a PR |
| Prepare an authored walkthrough | `npm run explain -- --project project.json --request walkthrough.json --out new-dir/` | `explanation.patch.json`, `explanation.preview.json` and `explanation-map.json` (not applied); see "Prepare an explanation walkthrough" below |

The scanner also skips nested repositories and git worktrees (any sub-folder with its own `.git`, `.claude/worktrees`, `.worktrees`), `node_modules`, build output and secret files.

Instruction files (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.github/copilot-instructions.md`) are read as `control` components in a **Declared rules** view (agents perspective), opened from a "Declared rules" card in the system context. Each card says "Declared rule; enforcement and effect UNKNOWN" and cites file:line for its sections and rule lines. A rule file is never an observation that the rule is followed, never a permission and never a measured effect; do not write it up as one. dbt models, dbt sources, plain SQL tables and Spark (`pyspark`) keep their own kinds and providers, and folders named after data layers (bronze, silver, gold) never create an environment. A scan is bounded and cancelable: `scanRepository(files,{signal})`, `scanToDocument` and `scanPickedFolder(list,now,signal)` throw an `AbortError` and return no model when the signal aborts; over the 480-component budget the coarse levels are kept first, and every file, view or item left out (over 512 KiB, beyond 6000 files, unparsable JSON/YAML, files views not created) is named in the report's `lost` list. `tests/independent-journeys.test.ts` checks these rules.

"Complete for the selected purpose" has one definition: `completeForPurpose(projectReadiness(project,{purpose}))` (or `projectCompleteFor(project,purpose)`, `src/intelligence/readiness.ts`) reports no `missing-required` gap for that purpose. Other gaps stay listed; it is never a completeness percentage, a runtime certificate or a review. A one-step, no-Git ProjectBrief is complete for `education` and needs an authored contribution for `portfolio`. The MCP tool list is the same for every selected document, a rich Galaxy pack or a one-node project.

Concept previews require an explicit audience. `--audience public` uses `publicDocument`; `--audience author` prepares a private projection of the selected view for a host that already has document access. Neither option grants access or changes publication visibility. The command reads only the selected document, preserves it, refuses existing output and writes `READY.json` last. READY records local preparation, not viewer, WebGL, T3 or publication qualification. `preview.packet.json` is a derived host sidecar, not an editable architecture, Mosaic load message or T3 preview descriptor. The selection-return helper is a candidate protocol; the Mosaic viewer is not wired to emit it. See `docs/contracts/concept-preview.md` for limits and mapping semantics.

### Prepare an explanation walkthrough (authored, private, not applied)

`npm run explain -- --project project.json --request walkthrough.json --out new-dir/` reads a document and a `diagramcloud.explanation-walkthrough` v1 request (`src/intelligence/explanationWalkthrough.ts`) and writes three files into a new directory: a revision-guarded `diagramcloud.patch`, the preview it would produce, and a map from each request step to its frame view, note and tour stop (`"applied": false`). It takes exactly these three arguments, reads at most 4 MiB of exact UTF-8 per input, refuses an existing output directory, and contacts nothing. The request is bound to the document by `projectId`, `baseRevision` and `baseFingerprint` (`walkthroughFingerprint`, a change detector and not a signature); any drift refuses before the output folder is created. The source document must already have a `tours` array, even an empty one: JSON Patch cannot assert absence, so a missing collection is refused rather than risk overwriting a tour added at the same revision.

Each step reuses the existing components and connections by stable ID (no cloned actors), adds a private frame view, a private note with its text, before/after state tables and an optional exact code excerpt marked "Frozen excerpt, not live code", and one private tour. Steps are presentation order, never causal order, elapsed time or a recorded run; `dependsOn` names explicit prerequisites only, and an absent link stays unknown. Nothing is applied: import the patch through the ordinary JSON review (Preview, Apply, one Undo); publishing any of it stays the author's decision in Edit mode. Six synthetic examples live in `examples/pro-expressiveness/` (`<case>.base.json` with its `<case>.walkthrough.json`, and the resulting `<case>.project.json`); see `docs/product/EXPRESSIVENESS.md`. `portfolioHtml(project, icons, {focusStory: true})` opts into the focused HTML reading (current view first, context breadcrumbs, code and tables first, explicit return to the last step); without the option the export is unchanged. In the App it is the export menu's own option, "Focused explanation HTML". In the V3 workspace the companion pane shows the selected component's explanation, code/state, related context (explicit depth, scope, direction and relation filters, bounded coverage) and evidence; opening a related item is a detour with an explicit return and never edits the document.

### Read a PM task snapshot (bounded, private projection)

The ordinary Studio JSON import path also accepts an explicit `datapass.owner-tasks/1` document through `src/development/pmTasks.ts`. It stages a separate private DiagramCloud Project: state columns, declared dependency view and full task/acceptance detail. It is a visual reader, not PM adoption, task editing, a synchronized board or execution. Use the normal import preview/Apply to open it. A repeated exact input already loaded is refused rather than replacing presentation edits; changed source bytes produce a separate snapshot.

This reader admits at most 60 tasks, 1000 local dependencies and 256 KiB of UTF-8 source. PM itself permits larger task documents; exceeding this visual subset is an explicit whole-input refusal, never silent truncation. Unknown fields, invalid dates, missing dependencies and cycles are refused. Desired dates do not create Gantt start/end intervals. Source `DONE` and `APPROVED` remain attributed text, not observations or DiagramCloud review. All actual task data starts private; public export intentionally has only a neutral empty shell. Authoring backup remains private and is not a PM task file. See [PM task import](contracts/pm-task-import.md) for scope and qualification limits.

### Project Intelligence inputs and outputs (1.24.0)

In the UI, **New analysis** selects Repository / Guided / Hybrid / Graph, purpose and Quick/Standard acquisition. Explicit optional Deep/Custom analysis profiles use bounded local parsers and reviewed projections. Read `docs/release-1.24/RELEASE_NOTES.md` for acquisition limits and `examples/project-intelligence/project-brief.json` for a synthetic no-Git brief. The generated `public/diagramcloud.project-brief.schema.json` is structural guidance; `validateProjectBrief`, `compileProjectBrief` (or `compileHybridBrief`), `validateDocument` and candidate review are all required. A ProjectBrief declares workstreams/systems/tasks, repository IDs/bindings and authored relationships; it never attests runtime. A task workspace displays evidence, never executes it.

`npm run intelligence -- brief --input examples/project-intelligence/project-brief.json --out <new-folder>` writes a new private candidate. `npm run intelligence -- inspect --input <document.json> --out <new-folder>` derives private readiness/asset context, not a new repository scan. Reuse existing review/patch guards to apply; reimport must retain authored text, positions, story, visibility, assets and evidence. Matching stable IDs remain; missing entries in partial input are not removals.

Explicit shared repository bindings in a ProjectBrief use private canonical declaration evidence: each scope's `brief-meta-<id>` block cites stable `brief-repository-<repository id>` sources. These are membership declarations, not inspected source findings. The authored node caption still cites the brief itself, so private repository membership does not turn that caption into source-derived content. Local paths never enter the compiled Project; no repository is read by brief compilation. Existing reviewed evidence is retained on conservative reimport; changing retained bindings needs an explicit reviewed patch. See [binding semantics](contracts/project-brief-source-bindings.md) and the [synthetic shared-repository brief](../examples/project-intelligence/shared-repository-brief.json).

Repository acquisition filters metadata before bounded reads, uses the existing scanner and selected safe Markdown/CSV, and yields/cancels without mutating the saved Project. Inventory content digest identifies inspected bytes; HEAD is a hint with unknown dirty state. Public sheets/context/assets must be derived after publicDocument. Do not copy private inventory text, filenames or counts into a public caption. A public node citing a private source has its source-backed summary/role omitted; explicit author source review or detachment is required to publish the caption. Manual assistance exchanges context and reviewed proposals; source documents are inert data, never tool instructions.

Generated diagnostics may supply a structured cause and suggested next step; see [gap advice](contracts/actionable-gaps.md). Missing metadata stays unclassified. Do not infer denied access from a generic read error, dynamic behavior from an ambiguous reference, stale revisions from age, or confirmed conflicts from a discrepancy candidate. Advice performs no action and grants no authority. Private selected-source/check collectors are unavailable in public presentation modes; switching audiences discards their transient state.

## 4. Formats you write

You produce one of these files and a person (or the CLI) applies it. You do not hand-edit `diagramcloud.json`.

### Project manifest: which repositories belong together

Membership is explicit: only repositories listed here enter the atlas. `host` is one of `github`, `gitlab`, `azure-devops`, `bitbucket`, `local`, `other`; `path` points at a local checkout to scan; relationships are declared (`planned`) unless a scan proves them.

```json
{
  "format": "diagramcloud.project-manifest",
  "version": 1,
  "project": {"id": "shop-platform", "title": "Shop platform (synthetic)", "summary": "Two services and their handbook."},
  "repositories": [
    {"id": "shop", "title": "Shop", "purpose": "Web shop and its API", "role": "application", "host": "github", "locator": "https://github.com/example/shop", "path": "../shop"},
    {"id": "billing", "title": "Billing", "purpose": "Payments ledger", "role": "service", "host": "gitlab", "locator": "https://gitlab.com/example/billing", "path": "../billing"}
  ],
  "relationships": [
    {"from": "shop", "to": "billing", "label": "charges orders", "kind": "query"}
  ]
}
```

A DataPass project file (`.datapass/project.json`) or the Claude Control galaxy map can be passed to `npm run atlas` instead; they are read as manifests, never written.

Galaxy provenance capture is default off. The CLI flag above, or the explicit browser checkbox before the existing Gallery/Hybrid Preview and Apply, records exact supplied app IDs and the local IDs actually allocated for a new candidate. The receipt uses existing private code evidence and stays excluded by `publicDocument` even if its visibility is changed. Authoring JSON retains it intentionally. The digest is SHA-256 of the decoded input text encoded as UTF-8, not original file bytes, a Git revision or producer authenticity. Namespace, upstream version and synthetic semantics remain unknown. Unsafe/oversized/inconsistent capture is unavailable without truncating IDs or changing the normal import. Capture into an existing local Galaxy target is unavailable; the same local Project ID does not establish the same source. `--previous` remains snapshot history only. Never use or edit this receipt to invent an identity association, permission, observation or historical ID repair. See `docs/contracts/galaxy-manifest-identity.md`.

### Design brief: how each view is drawn (presentation only)

A brief sets the figure type, at most two focal components (IDs that are in the view), a theme and a caption per view. It never changes components, connections, basis or observations. Apply it with `--brief`, or in the app: **Diagram Design** → Edit → **Read design brief…** → review → apply.

```json
{
  "format": "diagramcloud.design-brief",
  "version": 1,
  "projectId": "contoso-forecasting",
  "author": "your-agent-name",
  "views": [
    {"viewId": "overview", "type": "exploded", "focal": ["api"], "theme": "light", "caption": "One save, three levels: the lab, who may change a forecast, and where the data lands.", "why": "The story is the drilldown; the API is where a save is decided."}
  ]
}
```

### Revision-guarded patch: small edits to a document

RFC 6902 JSON Patch inside an envelope. `baseRevision` must equal the document's current `revision`, or the whole patch is refused. A path segment `@<id>` addresses an array item by its stable ID, so you never depend on array positions. The result must pass `validateDocument`; IDs, `revision` and `schemaVersion` cannot be changed. The person reviews every change in **JSON / AI** before it applies. This example adds a synthetic quantity to one connection (drawn by the Sankey figure):

```json
{
  "format": "diagramcloud.patch",
  "version": 1,
  "target": "project",
  "targetId": "contoso-forecasting",
  "baseRevision": 0,
  "summary": "Illustrative volume on the planner → Forecast UI connection.",
  "operations": [
    {"op": "test", "path": "/edges/@overview-e0/source", "value": "planner"},
    {"op": "add", "path": "/edges/@overview-e0/quantity", "value": {"value": 1200, "unit": "rows/day", "provenance": "synthetic", "note": "Illustrative, not measured."}}
  ]
}
```

Rename labels freely, keep IDs. To add a drilldown: create the child view (its `nodeIds`, `edgeIds`, `positions`), then set `childViewId` on the parent component. One level per component, no recursion.

**Validate a proposal before handing it over.** One validator (`src/core/proposal.ts`, `validateProposal`) sits behind the **JSON / AI** dialog, the CLI (`npm run intelligence -- validate-proposal --input proposal.patch.json --current doc.json --out new-dir/ [--applied ledger.json] [--author <name>]`, which writes `proposal-validation.json` and exits 1 on a refusal) and the MCP tool `diagramcloud_validate_proposal` (`{proposal, applied?}`). The same payload against the same document and applied ledger returns the same reason codes and sentences on every path: `wrong-target`, `wrong-project`, `stale-revision`, `replay`, `self-review`, `origin-relabel`, `not-applicable`, `malformed`, `unsupported-kind` and `provider-launch`. Origin comes from the path, never from the payload: the dialog and the CLI are `imported`, MCP is `ai` with the client name, and `author` only when a person names themself with `--author`. A non-author proposal cannot mark an observation reviewed, shareable or public, cannot review or reject a concept mapping, cannot accept a choice or record who decided, and cannot change who suggested a mapping, choice or variant; those stay the author's actions in Edit mode. Replay is detected by a digest of the target and operations (`contentDigest`), so an applied proposal cannot apply twice, even after Undo or with its `baseRevision` relabelled; the browser keeps its ledger of digests (no content) locally. MCP validates against the public projection, so a proposal that touches private facts is reported `not-applicable` there. Only `diagramcloud.patch` is a supported proposal kind; a payload that asks to start a provider, model or command is refused with `provider-launch`, and validation never applies, executes or contacts anything.

### Choices: optional rationale on a component or view

A node or view may carry `choices` (defined in `src/core/model.ts`, checked by `validateDocument`). Each choice has a stable `id`, `title`, `goal`, one to twelve `options` (`id`, `label`, optional `summary`), optional `recommendedOptionId`, `reasons`, `tradeoffs`, `assumptions`, `revisitWhen`, `sourceIds`, `visibility`, an `origin` (`author`, `ai` or `imported`), an optional `suggestedBy` (who recommended it; an agent records its own name) and a `status`. A `candidate` (the default, and what an AI writes) never carries `chosenOptionId` and is never shown as accepted. An `accepted` decision must record `chosenOptionId`, `decidedBy` and `decidedAt`, and `validateDocument` refuses one whose `decidedBy` is the same person or agent as its `suggestedBy` (names compared ignoring case, accents, spacing and punctuation): an AI recommendation is not a decision. The import review cautions on every choice that arrives accepted, changes to accepted or changes its accepted option or decider. Keep an imported decision's author, date and sources unchanged. There are no numeric scores or savings. Documents without `choices` stay valid; public export keeps only public choices whose sources are public. Add or change choices with a `diagramcloud.patch` (for example `add /nodes/@<id>/choices`) or in the Edit-mode **JSON drawer**.

An option may carry `compatibility`: evidence, recorded by a named person, for one requirement of the substitution check (`src/intelligence/learning/substitution.ts`) of the component that owns the choice: `{"requirementId": "out:overview-e0", "requirementText": "Provides the …", "verdict": "satisfied", "sourceIds": ["src-adr"], "blockIds": [], "recordedBy": "Julian", "recordedAt": "2026-10-17"}`. Requirement IDs are `role:<node>`, `in:<edge>`, `out:<edge>` and `assumption:<choice>:<n>`; `verdict` is `satisfied` or `violated` (a violation wins). `validateDocument` refuses a record without any citation and two records for one requirement. Only citations that resolve to a project source or a non-synthetic evidence block count: a synthetic block never establishes compatibility, and a matching name, provider or catalogue family is never proof. With every requirement satisfied the check reads "Compatible per cited evidence · not a verification". Evidence for a requirement that no longer exists, or whose wording changed since `requirementText` was recorded, is shown ignored and never rebound. Recording or changing evidence changes the decision's fingerprint, so a reviewed decision becomes review-needed. The person records it in Edit mode (Inspector, **Choices and decisions**, an alternative's **Substitution check**, `recordCompatibility` in `src/core/decisionReview.ts`); an agent may propose a record in a `diagramcloud.patch` for the author's review but never records one under a person's name, and a recommendation cannot record evidence for itself. Public export keeps only public citations and drops a record left with none.

The **JSON drawer** (`src/ui/JsonDrawer.tsx`, logic in `src/core/jsonDraft.ts`) edits the whole project or one component by its exact stable ID. It shows the applied model, the current draft and the last valid preview separately; keystrokes never save, an invalid draft keeps the last valid preview and disables Apply, and Apply revalidates against the live revision as one undoable revision. A draft written before a newer edit is refused without mutation. It is absent in Portfolio and Present.

### Variants: a change set against a known baseline

A document may carry `variants` (optional; `src/core/model.ts`, logic in `src/core/variants.ts`, Edit-mode **Variants** tab in `src/ui/Variants.tsx`). A variant is a named change set, never a second diagram: a stable `id`, `title`, `viewId`, JSON Patch `operations` (`add`, `remove`, `replace`, `test`; `@id` addressing; only `/nodes/@<id>…`, `/edges/@<id>…`, `/nodes/-`, `/edges/-` and its own `/views/@<viewId>/…`), an `origin` and optional `suggestedBy`, and a `base` recorded when it is created: the project revision and a fingerprint of the view, its members and every item the operations address. Components and connections it adds take IDs starting with `<variant id>.`, and `validateDocument` refuses a canonical ID inside a variant's namespace, so candidate-local IDs never collide with canonical ones. Selecting a variant compares it with its baseline (the architecture delta, `compareView` in `src/export/design/delta.ts`, plus the change preview) and changes nothing; a variant is never accepted by being selected. When the baseline changes the variant is stale: comparison and Apply are refused until the author explicitly rebases it. Apply runs the operations and the variant's removal as one revision-guarded `diagramcloud.patch`, committed as one undoable revision. Write a variant with a `diagramcloud.patch` (`add /variants`), never by editing the canonical components. Local, test and production instances are delivery declarations, not variants. Public export drops every variant.

### Tours: a presented sequence over stable subjects

A document may carry `tours` (optional; `src/core/tours.ts`, **Tours** tab in `src/ui/Tours.tsx`). A tour has a stable `id`, `title`, `visibility`, the `sourceRevision` it was recorded at and `stops`; each stop stores its selected `viewId`, the stable IDs of its `subjects` (`node` or `edge`), a content `fingerprint` taken when recorded, and `narration`. A tour is a presented sequence, not timing and not a run. Anchors are not repaired: playing derives each stop as current, stale (content changed since recording), missing (view or subject gone) or omitted, and a stale or missing anchor fails visibly. Public export keeps public tours only; a subject that is not public is dropped and the stop is marked `omitted: "subjects"`, a stop on a non-public view becomes `omitted: "stop"` with no view, subjects or narration, and neither names nor counts what was hidden. Narration of a public tour is published as written.

**Evidence for the measured figures.** Sankey, Gantt and Comparison draw only supplied evidence; otherwise they are withheld and name what is missing, with the same words in Studio, SVG, the figure book, the manual and the deck.

- A connection `quantity` may add `measurementId` (the identity of one supplied measurement), `scope` and `window` (`{"from": "2026-09-01", "to": "2026-09-07"}`). The Sankey draws one unit, scope and window; others are listed, never summed. Two connections with equal labels or endpoints stay two flows; one `measurementId` on two connections of one scope is reported as ambiguous and never counted twice. Zero stays zero.
- A schedule block is an evidence block `{"type": "schedule", "timezone": "date-only", "items": [{"id": "build", "label": "Build", "nodeIds": ["etl"], "start": "2026-10-01", "end": "2026-10-05", "basis": "supplied"}]}`. `timezone` is `date-only` (calendar days; an end date is the last day) or a zone such as `UTC` or `Europe/Paris` (then `start`/`end` are timestamps with an offset). Give `end` or an ISO 8601 `duration` (`P5D`, `PT6H`); both must agree. `basis` is `supplied` or `estimate`, and estimates stay drawn as estimates. An end before its start, an unknown component, a date mixed with a timestamp or one item ID with two intervals is refused visibly. Schedule items are dated evidence, not runs or observations.
- A metrics item may add `measure`: `{"metric": "p95 latency", "value": 420, "unit": "ms", "scope": "checkout API", "window": {"from": "2026-09-01", "to": "2026-09-07"}, "basis": "measured", "role": "baseline"}`. `basis` is `measured`, `estimate` or `derived`; a synthetic block never carries `measured`. The comparison needs one `baseline` and one `current` reading of the same metric, unit and scope over windows of the same length; a zero baseline has no percentage. The difference is derived arithmetic, not a cause, and no money or time saving is inferred. The figure says "measured difference" only when both readings are `measured` in non-synthetic blocks that cite a source; otherwise it says "not a measured saving" and gives the reason (an estimate, a derived value, synthetic readings or no cited source).
- In Edit mode, schedules and readings have forms (`src/core/evidenceForms.ts`): **Add evidence → Schedule** or an attached schedule block edits the time basis and each item's dates, duration, basis and components; a metrics row's **Baseline or current reading** edits its `measure`. Each error is shown beside its field, nothing is repaired or converted, and applying is one revision and one Undo.

### Compatibility, image identity and repository saves

- **Schema compatibility** (`src/core/moduleCompat.ts`). A whole document with a `schemaVersion` other than 1 is refused and nothing is imported. Top-level keys this version does not know are reported as unsupported modules; the JSON / AI dialog imports the rest only after the author confirms that exact list ("Import the rest without them"), and the unknown modules are dropped, not kept aside: they grant nothing. Fields inside known modules stay strict. Do not add a top-level key and expect it to survive an import.
- **Image digest and duplicates** (`src/core/assetIdentity.ts`). An attached image records `digest` (`sha256:` and 64 hexadecimal characters) computed locally from its stored bytes; an import whose digest does not match its bytes is refused. A Drive `md5Checksum`, ETag or modified time is never a digest. Attaching identical bytes offers **Reuse existing image** or **Keep both**; keeping both records `keptDistinctFrom` on the new asset, which survives save, reopen and repeat import and is never asked again for that pair. The same name with different bytes is flagged as a possible duplicate and never merged. Public copies drop `keptDistinctFrom`. Never write a digest you did not compute from the bytes.
- **Uncertain repository saves** (`src/bridge/sidecar.ts`). When writing `.datapass/diagramcloud.json` fails after the file was opened for writing, the save reports "Outcome unknown, not saved" and keeps the attempted revision, hash and size in memory for that folder. The next save re-reads the file first: if it holds exactly that attempt it counts as saved; anything else is a conflict naming the attempt. A failed write is never retried blindly; reopening the repository file for review clears the receipt.

## 5. Choosing a figure

Run `npm run design -- doc.json --out figures/` and read `figures/suggestions.json` (`diagramcloud.design-suggestions/1`): for each public view, the five best figure types with the fact behind each ("a numeric table on Input rows", "6 child views below this one"). Then choose by the question the figure must answer:

| Question | `type` | Needs |
|---|---|---|
| How do the parts talk to each other? | `architecture` | (default) |
| What sits on what? | `layers` | several component kinds |
| Overview, then what is inside one part | `exploded` | drilldown views |
| Where is everything? | `tree` / `treemap` | drilldown views |
| Who owns which step? | `swimlane` | repositories or layers |
| What is the path of one request? | `sequence` | connections (order from connections, not timing) |
| What is the walkthrough? | `timeline` | story steps |
| What are the numbers? | `chart` / `line` / `heatmap` | a numeric table evidence block |
| Where does it run? | `deployment` | declared delivery instances or provider fields |
| How much is backed by source? | `matrix` | basis and confidence |
| What touches this part? | `hub` / `radial` | a component with 3+ connections |
| What enters and leaves? | `context` | entry points and sinks |
| Which parts are in which designed state? | `status` | designed statuses |
| Where does this come from and go? | `lineage` | a flow 3+ steps deep |
| How much moves along each connection? | `sankey` | `quantity` on connections |
| When does each dated item start and end? | `gantt` | a schedule evidence block on a component: items with supplied dates or declared estimates (story order is never timing) |
| Did a metric change between a baseline and now? | `comparison` | metrics items with a measure: one baseline and one current reading of the same metric, unit, scope and window length |
| How do supplied signed increments accumulate in table order? | `waterfall` | One public numeric table column, at most eight readable rows with omissions reported; running sums are derived, never observed or causal totals |
| Which repositories moved? | `atlas` | an atlas document |

A figure reads well up to about 9 components and 12 connections; beyond 24, use drilldown views. Focal components (0–2) get the accent colour: pick where a decision is made, where data lands, or what changed.

## 6. Worked flows

**Graph a codebase and hand over figures**

1. `npm run scan -- ../my-repo --out .local/my-repo.json`
2. `npm run design -- .local/my-repo.json --out .local/figures` and read `suggestions.json`.
3. Write `.local/brief.json` (section 4), then `npm run design -- .local/my-repo.json --brief .local/brief.json --out .local/figures --pdf`.
4. Give the person `book.html` / `book.pdf`, or the brief to apply in the app.

**Graph several projects and track them**

1. Write `project.manifest.json` with explicit members and declared relationships.
2. `npm run atlas -- project.manifest.json --out .local/atlas.json`; keep the file.
3. Next time: `npm run atlas -- project.manifest.json --previous .local/atlas.json --out .local/atlas2.json`, then `npm run design -- .local/atlas2.json --type atlas --out .local/figures` to see what moved.

**Propose an edit**

Write a `diagramcloud.patch` against the current `revision`, include `test` operations for what you rely on, and ask the person to review it in **JSON / AI**. Never write observations, `reviewedAt`, or "shareable" flags: those are the author's decisions.

## 7. Never

- Invent a component, connection, repository, revision or number that no scan, manifest or source produced.
- Present a scan as observed or verified, or a synthetic value as a result; never drop or soften a provenance label.
- Edit `diagramcloud.json` by hand, mark an observation reviewed, or promote a synthetic evidence block to back an observation (`validateDocument` refuses it; do not work around it).
- Commit a real private atlas or names from it (keep it in `.local/`, which is git-ignored), or read secret files.
- Use `eval`, raw HTML from imported JSON, or network fetches in exports.
